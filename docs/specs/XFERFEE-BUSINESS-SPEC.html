The chain in one picture

Every business day the scheduler submits XFRDAILY, which runs PROC XFERFEEP: three programs, three hand-offs through fixed-length generation datasets, one database commit.

STEP010 · CBXFR01C

Extract

Pick today's transfer transactions, resolve card → source account → book, and write a slim 120-byte extract.

DALYTRAN, CARDXREF, ACCTDATA→ XFER.EXTRACT(+1)
STEP020 · XFERFEE

Price & post

Look up the fee rule for the book on the transfer date, compute and cap the fee, move balances, write the fee file and the Db2 ledger.

XFER.EXTRACT(0), ACCTDATA, CTL_XFER_PARM→ ACCTDATA.XFER(+1), XFER.FEES(+1), XFER_FEE_LEDGER
STEP030 · CBXFR03C

Reconcile

Print every fee with subtotals per book and a grand total; flag an empty day with RC 4.

XFER.FEES(0)→ XFER.RECON.RPT(+1)

Return codes: 0 clean · 4 warning (unmatched card, empty fee file) · 8 abend (no/ambiguous fee rule, unknown account, SQL error). STEP030 runs only if STEP020 returned ≤ 4.

How money is represented

All amounts are exact decimals — never floats. Transaction and balance amounts are S9(n)V99 (two implied decimals). The fee percentage is S9V9(6) — e.g. 1.25 % is stored as 0.012500. On the fee file the amounts are COMP-3 packed decimals; in the master file they are zoned display digits. The rules below are about the values; the layouts are in the companion Markdown spec §2.

Extract — which transfers count

BR-1Only transaction type 08 is a transferCBXFR01C.cbl

A daily transaction is a transfer fee candidate if and only if TRAN-TYPE-CD = "08". Nothing else — amount sign, category, source, merchant — matters for selection.

Edge cases
Exact two-byte match; "8 " or "08" in another field is not selected. The non_transfer fixture mixes types 01/02/08 and only the 08 record is extracted.
BR-2Card → source account via the cross-referenceCBXFR01C.cbl

The transaction's card number is looked up in CARDXREF; the first matching row supplies the source account id. Up to 500 xref rows are held in memory.

If missing
Logs CBXFR01C: CARD NOT FOUND <card>, counts it as unmatched, skips the record (see BR-5).
BR-3Book comes from the source accountCBXFR01C.cbl

The source account is looked up in the account master and its ACCT-GROUP-ID becomes the transfer's book. The target account's book is never consulted — a cross-book transfer is priced by the payer's book.

If missing
Also counted as "unmatched" (the SYSOUT label says CARDS but the count includes accounts — Q12).
BR-4Target account is parsed out of the descriptionCBXFR01C.cbl

The target account id is the 11 characters at positions 14–24 of TRAN-DESC (i.e. after the literal XFER TO ACCT ). The extract record carries: tran id, date (first 10 chars of the origin timestamp), source acct, target acct, book, amount.

The layout of the description is a convention, not a validated contract. A description in any other shape yields garbage in the target id and an abend downstream (BR-11) — Q4.
BR-5Unmatched records are a warning, not a failureCBXFR01C.cbl

The step prints RECORDS READ, TRANSFERS SELECTED, UNMATCHED CARDS. If any record was unmatched the step ends with RC 4; the transfers that did match are still written.

In real JES the chain would continue past RC 4; the estate's runner stops after any non-zero step. Which behaviour to port is a business decision — Q9.

Fee rule selection

BR-6Whole account master in memoryXFERFEE.cbl

The posting step loads the account master into a table of at most 500 rows before processing. Every loaded row is rewritten at the end (BR-14), whether or not it changed.

BR-7Rule = book + date window, start inclusive, end exclusiveXFERFEE.cbl · CTL_XFER_PARM

For each transfer the fee rule is the single CTL_XFER_PARM row where

BOOK_ID = book  AND  EFF_DT <= transfer_date  AND  transfer_date < EXP_DT
Boundary
On the day a new rule takes effect (EFF_DT) the new rule wins; the old rule's EXP_DT is the first day it no longer applies.
None found
SQLCODE +100 → NO FEE RULE, RC 8, ROLLBACK.
Overlap
More than one row (SQLCODE −811) → RC 8. Rules must not overlap within a book.
Rule date
The matched row's EFF_DT is carried onto the fee record for audit.
Proven by rate_change: RETAIL has 1.25 % with EXP_DT 2024-06-15 and 1.50 % with EFF_DT 2024-06-15. Three 100.00 transfers on 06-14 / 06-15 / 06-16 are charged 1.25 / 1.50 / 1.50.

Fee calculation

BR-8Fee = amount × rate, rounded half away from zero to the centXFERFEE.cbl COMPUTE … ROUNDED
fee = round_half_up( amount × FEE_PCT , 2 decimals )

COBOL ROUNDED into an S9(9)V99 target keeps exactly two decimals and rounds a half-cent away from zero — not banker's rounding, not truncation. The full-precision product is never stored.

Proven by half_cent: 2.00 × 1.25 % = 0.0250 → 0.03; 3.00 × 1.50 % = 0.0450 → 0.05; 11.00 × 1.50 % = 0.1650 → 0.17; INSTL 5.00 × 0.50 % = 0.0250 → 0.03. Banker's rounding would give 0.02 / 0.04 / 0.16 / 0.02; truncation likewise. The recorded grand total is 0.46.
BR-9Cap applies only when the fee is strictly above itXFERFEE.cbl
if fee > FEE_CAP: fee = FEE_CAP; CAP_APPLIED = "Y"  else  CAP_APPLIED = "N"

The comparison is against the rounded fee. A fee exactly equal to the cap is charged at the cap but flagged N.

Whether "fee equals cap" should be reported as capped is a business question — Q2. The port preserves the current strict behaviour.
Proven by at_cap: RETAIL 5,000.00 × 1.25 % = 62.50 → capped to 25.00; INSTL 200,000.00 × 0.50 % = 1,000.00 → capped to 500.00. Both flagged Y.
BR-10Zero-amount transfers are still postedXFERFEE.cbl

A transfer of 0.00 is not filtered out: fee is 0.00, cap flag N, balances are updated by zero, a fee record is written and a ledger row inserted. It appears on the report as a 0.00 line.

Negative amounts are not special-cased either; the fee would be negative and the cap test would never fire — Q3.

Posting

BR-11Both accounts must exist in the masterXFERFEE.cbl

Source and target account ids are searched in the in-memory master. If either is missing the step abends with RC 8 and rolls back all database work.

Duplicates
The lookup keeps scanning after a hit, so the last matching row wins — the opposite of the extract step (first match). Only matters if the master has duplicate ids — Q7.
Self-transfer
Source = target is allowed; the same row receives both sides of the movement.
BR-12Balance and cycle movementsXFERFEE.cbl
source.CURR_BAL −= amount + fee
source.CURR_CYC_DEBIT += amount + fee
target.CURR_BAL += amount
target.CURR_CYC_CREDIT += amount

The payer bears the fee; the payee receives the full amount. Credit limits, account status and expiry are not checked — Q8.

Proven by default: account 1 starts at 1,000.00 and sends 100.00 with fee 1.50 → balance 898.50, cycle debit 101.50; account 2 starts at 500.00 and receives 100.00 → balance 600.00, cycle credit 100.00. Accounts 3, 4, 5 and 8 are untouched but still rewritten (BR-14).
BR-13One fee record + one ledger row per transferXFERFEE.cbl · XFER_FEE_LEDGER

Each posted transfer writes a 100-byte fee record (tran id, date, source, target, book, amount, rate, fee, cap flag, rule effective date) and inserts the matching row into XFER_FEE_LEDGER:

INSERT INTO XFER_FEE_LEDGER
   (TRAN_ID, TRAN_DT, SRC_ACCT_ID, TGT_ACCT_ID, BOOK_ID, TRAN_AMT, FEE_AMT, CAP_APPLIED)
VALUES (…)
TRAN_ID is the primary key: re-running a day that has already been posted fails on the insert (RC 8) — Q14.
BR-14Totals, full master rewrite, single commitXFERFEE.cbl

After the last transfer the step prints TRANSFERS POSTED and TOTAL FEES (signed, in cents), writes every loaded account row to ACCTDATA.XFER(+1), and issues one COMMIT. Any failure before that point rolls back all inserts — the ledger is all-or-nothing per run.

The updated master is written to a new generation; nothing copies it back over ACCTDATA.PS, so a second run starts from the original balances — Q10.

Reconciliation report

BR-15Detail lines in input order, subtotal on every book changeCBXFR03C.cbl

The report lists each fee record as read (no sorting). Whenever the book differs from the previous record's book a SUBTOTAL <book> line is printed for the run just ended.

Because the fee file is in extract order, interleaved books (RETAIL, INSTL, RETAIL) produce three subtotals, not two — Q13.
BR-16Final subtotal, grand total, fixed pictureCBXFR03C.cbl

After the last record a final subtotal and a GRAND TOTAL line (with the record count) are printed, and CBXFR03C: GRAND TOTAL FEE goes to SYSOUT. Amounts use the edited picture Z(8)9.99-: leading zeros suppressed, trailing - for negatives, blank otherwise.

BR-17An empty day is a warningCBXFR03C.cbl

If the fee file has no records the report contains only the headings, SYSOUT shows CBXFR03C: NO FEE RECORDS, and the step ends with RC 4 so operations can see that nothing was posted.

Job control

BR-18Step order, condition codes, generationsXFRDAILY.jcl · XFERFEEP.prc · DEFGDGX.jcl

Steps run strictly in order. STEP030 carries COND=(4,LT,STEP020) — it is bypassed if posting returned more than 4. Each step writes a new generation (+1) and reads the current one (0) of the four GDG bases (XFER.EXTRACT, ACCTDATA.XFER, XFER.FEES, XFER.RECON.RPT), each keeping the last five generations. The job's MAXCC is the highest step RC.

Open questions for the business owner

Behaviour the code exhibits but does not obviously intend. The Python port preserves the current behaviour in every case; decisions here would be follow-up changes.

Q1

Comments vs table

Source comments still describe a "$2.50 flat / 1 %" fee; the table drives 1.25 % / 1.50 % with caps. Comments are obsolete.

Q2

Fee equal to cap

Flagged N today (strict >). Should it be Y?

Q3

Negative amounts

Not rejected; produce a negative fee and credit the payer. Runtime reads a } over-punch as positive.

Q4

Target from description

Positions 14–24 of free text are trusted as an account id.

Q5

Asymmetric failures

Unknown source card → RC 4 skip; unknown target account → RC 8 abend of the whole run.

Q6

500-row tables

Masters above 500 rows are silently truncated.

Q7

Duplicate account ids

Extract uses first match, posting uses last match.

Q8

No eligibility checks

Status, credit limit, expiry are never consulted.

Q9

RC 4 continuation

JES would continue past STEP010 RC 4; the runner stops. Which is intended?

Q10

Master never copied back

Balances are written to a new generation only.

Q11

Dead fields

Unused copybook fields and DB2PARM entries.

Q12

"UNMATCHED CARDS"

Also counts unmatched accounts.

Q13

Unsorted subtotals

Interleaved books yield repeated subtotals per book.

Q14

Re-run

Duplicate TRAN_ID makes a re-run abend RC 8.

Q15

Report format

DCB says RECFM=FBA (133); program writes LINE SEQUENTIAL text.
